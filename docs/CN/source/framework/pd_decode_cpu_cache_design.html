PD Decode 节点 CPU Cache 设计

用 D 的本机 CPU 缓存复用 prompt KV，减少跨节点传输，沿用现有 PD 协议。

核心边界：混合注意力跳过 P 前，KV 与对应运行态必须全部就绪；仅有 CPU KV 命中不够。支持普通多 DP，与 --enable_dp_prompt_cache_fetch 的组合首版互斥。

1. 整体流程

P 是 Prefill 节点，负责完成 prompt 计算；D 是 Decode 节点，负责后续生成。本方案让 D 先复用本机缓存，减少 P→D 的 KV 传输。

请求初始化时先构建哈希和页长度列表，再统一处理 Decode hybrid 的完全命中边界。外部匹配服务直接查询这些页面，之后再查询 GPU 已有前缀；CPU 命中更长且值得采用时，将新增部分搬回 GPU。恢复完成或确定无需加载后，通过一次性回调续接 PD 接收任务初始化。生成结束时，按现有策略写回 CPU，供后续请求复用。

图 1 · 图中展示需要 P 补齐的主路径；本地已就绪时的接续方式见第 3 节。取消与失败见异常回收。

请求有两条接续路径：本地已具备计算条件，由 D 计算最后一个 prompt token；否则由 P 补齐数据并提供首 token，D 接着生成。具体条件见第 3 节。

2. 方案与范围

复用现有 CPU 缓存服务、异步搬运和放置策略，补齐 D 的请求接入与就绪控制。继续使用 --enable_cpu_cache；P 是否启用 CPU 缓存可独立配置，PD 通信协议不变。

本文用词含义
KVfull-att 层按 token 保存的历史数据。
运行态 / checkpoint混合注意力中的线性注意力、卷积等状态；checkpoint 是它在某个前缀位置的可恢复快照。
命中 / 就绪命中表示找到可复用数据；就绪表示所需数据已恢复完成，可以被计算使用。
方案保留三条边界
  • CPU 恢复完成后，才发布 PD 接收任务。
  • D 的混合注意力 CPU 缓存只保存 KV；运行态通过本地完整缓存或 P 的末尾状态获得，不能省略。
  • 支持普通多 DP；D CPU cache 与生效的 DP shared 前缀拉取互斥。

缓存对象是跨请求复用的 prompt KV，不包含 decode 输出。命中仍需占用 GPU 显存，因此不会扩大活跃请求可用的上下文容量。

选择依据

只删除断言或只增加写回都没有读复用；同步等待会阻塞其他请求。异步恢复可复用现有机制，KV-only 则避免新增中间 checkpoint 的传输和槽位管理，代价是 CPU 命中不能独立满足混合注意力的完整恢复条件。

3. 何时可以跳过 P

设 N 为 prompt 长度。当前普通 PD 会保留最后一个 prompt token：本地具备前 N−1 个 token 的完整计算条件时，由 D 计算最后一个 token 并产生首 token；否则需要 P 参与。

混合注意力的完整条件：前 N−1 个 token 的 KV 与同一位置的所有所需运行态，均已恢复完成。

KV 命中长度不能代替运行态。比如 prompt 有 513 个 token，CPU 只有前 512 个 token 的 KV，没有对应运行态；此时直接让 D 计算第 513 个 token，可能使用初始或旧状态而产生错误结果。

场景P 是否参与接续方式
普通 PD，完整注意力模型的前 N−1 个 token KV 已就绪可跳过保留零长度握手，由 D 计算最后一个 prompt token，产生首 token。
普通 PD，混合注意力的 KV 与 N−1 位置运行态都已就绪可跳过沿用本地完整缓存恢复路径，由 D 产生首 token。
普通 PD，混合注意力仅从 CPU 命中 KV，或只有部分前缀必须参与P 补齐缺失 KV，并提供处理完 N 个 prompt token 后的运行态和首 token；D 从后续 token 继续。
Prefill-first，首 token 后仍需 D 继续生成，包括 KV 命中至 N−1仍然参与D 至少接收一个真实 KV token；混合注意力另收 N 位置运行态，首 token 放在最后任务中。

Prefill-first 若在 P 生成首 token 后就已结束，例如只请求 1 个输出 token，Master 不会选择 D，也不会触发 D 的 CPU 加载或写回。预热 D 缓存的测试必须让请求实际经过 D。

用完整页回退保留现有协议

现有普通 PD 在收到 N−1 命中时就会停止 P 的生成，Master 也不再等待 P 首 token。因此，Decode hybrid 请求在初始化末尾检查：末页结束位置加 1 恰好等于 N 时，同步缩短 CPU 哈希列表与页长度列表，退掉最后一整页，让 P 继续参与。构建过程不嵌入退页规则；匹配服务和推理搬运层直接使用初始化结果。

“所有缓存块命中”不一定是 PD 完全匹配，还要比较实际覆盖位置。例如 CPU 页长 256：N=513 时候选到 512，需退到 256；N=514 时同样候选到 512，但还缺尾部，保留两页即可。普通 PD 和 Prefill-first 统一采用该规则；Prefill-first 仅在这一边界少复用一页，仍按原协议接收尾部 KV 和运行态。完整注意力模型不回退。

回退不能靠加载后少报长度，也不能把完整页截成不支持的碎页。两个 CPU 列表同步缩短后，匹配和写回都不再使用末页；仍沿用小命中跳过搬运等原有策略。GPU radix 哈希保持完整，已有 KV 与同长度运行态的本地完整命中不回退。N=1 时没有 CPU 页，无需裁剪。

实际采用多少前缀

G 是 GPU 命中长度，H 是 CPU 候选长度。先按上述规则选择候选，再检查容量和恢复条件；L 是最终采用且已就绪的前缀长度。未采用 CPU 时沿用 G，新增复用量为 L−G，不能把 GPU 与 CPU 命中相加。

图 2 · CPU 命中长度是“从开头累计到哪里”，并不是额外命中多少。统计新增 CPU 命中时应扣除 GPU 命中。

CPU 页长与 PD 页长可不同，但分别满足模型和布局对齐。短请求或无可用完整页时沿用原路径；CPU 哈希仍保留最后一个 token 不匹配。

4. 请求如何异步推进

搬运期间请求留在等待状态，推理循环继续处理其他请求。下面是需要 P 补齐时的时序。

图 3 · 先确认 CPU 恢复完成，再发布接收任务；收到 P 的 KV 和所需运行态后才计算。本地完整命中的普通 PD 沿用零长度握手。

阶段进入下一阶段的条件
CPU 恢复所选 KV 已搬回 GPU，且副本内各 TP rank 对完成状态达成一致；标记 load 完成并归还 CPU 页引用，再清空、执行一次性回调，创建 PD 接收任务。未命中或跳过加载也在归还引用后立即续接。
PD 接收本地接收和复制全部成功，本路径所需运行态已恢复；随后允许计算。失败或取消进入回收流程。
生成结束 / CPU 写回按放置策略决定是否写回；写回完成后发布可复用页，再释放 GPU 和请求资源。

任务未创建时，完成计数相等也不能放行。CPU load 仍在进行时，公共就绪检查先拦住请求；load 完成推进中执行一次性回调，然后才进行 PD 就绪检查，因此无需额外的“任务已提交”标志。P / D 都先调用公共检查，再处理 PD 取消与完成状态；搬运中不重复提交或提前释放资源。取消且未提交的请求只做终态清理。

状态检查只限制“跳过 P”和“开始计算”。CPU 前缀没有对应运行态时，仍需创建 PD 接收任务，接收 P 提供的末尾状态，不能等待一个不会产生的中间 checkpoint。

多卡与显存

复用现有完成事件、组内同步及主 rank 归还 CPU 引用的机制；同一 DP 副本内各 TP rank 对前缀、提交时机和任务数保持一致，不增加跨 DP 前缀交换屏障。

CPU 命中不减少最终显存预算。恢复后重新检查尾部容量，不足时在整组发布前安全终止；不发布半组任务，也不盲目重试已发布任务。

5. 缓存保存什么

角色CPU 缓存内容恢复后的用途
Normal / Prefill保持现有 KV + 所需运行态快照。恢复到对应前缀后继续 prefill。
Decode只保存 full-att KV，不建立中间运行态快照。减少 P→D 的 KV 传输；是否能本地接续按第 3 节判断。

P 参与时会完成 prompt 计算，因此 D 可以接收 P 的末尾运行态，而不必恢复 CPU 前缀终点的中间状态。这就是“不新增中间 checkpoint 传输”的适用前提。

运行态快照绑定确定的前缀位置：N 位置不能代替 N−1 或其他位置，main / draft 的全部所需状态都须一致。CPU KV 命中不生成 GPU radix checkpoint；保留 D 禁用大页、无合法快照不插入 radix 的规则，不能借用末尾状态伪造中间快照。

无可缓存 KV 时，开启 CPU cache 会由现有 CPU 元数据初始化的非空页校验报错，不额外提前构建布局，也不自动关闭缓存。量化字段、压缩索引等仍由现有布局完整处理。

如果希望 CPU 完整命中后也能跳过 P

需要让 CPU 缓存同时保存并恢复对应前缀的运行态。这会改变缓存内容和状态生命周期，不属于当前 KV-only 方案；不能只放开“完全匹配”分支。

维度规则
P / D 配置P 可不开 CPU cache；P/D 的 CPU 页长可不同，也不必等于 PD 页长。原有模型、TP 分片和传输兼容要求保留。
TP / 普通 DP / 传输保留普通多 DP、副本内 TP 和既有 overlap、NIXL / NCCL 支持范围；验证接收端完成语义。
放置策略legacy 可写 GPU+CPU；adaptive 可能选 GPU-only。验收需实际选中 CPU，不能仅凭没有写回判断失效。
prompt logprobs / diverse保持现有跳过、主请求匹配 / 写回及各角色功能校验，不扩大已有能力。
多模态D 不重新编码，使用 P 提供的 prompt token IDs 构建 CPU 缓存哈希；当前两种 PD Master 均向 D 传递空多模态参数。加载层仅根据已有的 mm_input_spans 裁剪恢复终点，空 spans 不触发裁剪；尚无“多模态信息不足时自动跳过 CPU 恢复”的判断，多模态组合仍需单独验证。
磁盘沿用原目录规则：未配置时使用含服务名的临时目录，显式配置时直接使用指定目录。不新增 Decode 专用名称或子目录。

匹配超时现有 0.5s 仅检查入队等待，不覆盖处理中的 READY 轮询。保留服务架构，验收等待中取消 / 异常；若发现无界等待再修该生命周期。

6.1 不支持与 DP shared 同时启用

DP shared 特指 --enable_dp_prompt_cache_fetch 的跨 GPU 前缀拉取。关闭它仍可保留普通多 DP 和实例内共享 CPU cache；各副本只处理自己的请求。

图 4 · 各 DP 副本独立恢复自己的请求，共享实例内 CPU 缓存；不进行跨 GPU 的前缀拉取。

若支持组合必须补齐的契约
批次与屏障普通 DP shared 按全批次行号建立临时请求，D 只初始化归属请求。须统一集合和行号，保证节点 collective 次序一致，不能按各副本 load 完成条件进入屏障。
数据就绪计划恢复的长度不代表数据已可读取。跨 DP 消费前，必须确认 CPU 搬运和 PD 本地复制完成。
运行态一致性跨 DP 复制会涉及运行态，KV-only 前缀却没有对应快照；需要保证 KV 与状态处于同一位置，或另设计仅复制 KV 的路径。
源请求保活临时源对象须等复制完成再释放，覆盖取消；CPU 匹配引用只能由唯一消费者 load / deref，非归属 DP 不写终态。

6.2 组合规则

  • D + CPU cache + fetch 关闭：允许单 / 多 DP 与副本内 TP。
  • D + CPU cache + fetch 开启且 dp>1：两种 PD 模式都报错；每节点仅一个 DP 的拓扑也不额外豁免。
  • dp≤1：在资源分配前归一化关闭无效 fetch；D 不开 CPU cache 或其他角色不新增该限制。D fetch 的入口旁路另记问题，不视作已验证功能。

代价：无法直接命中只在其他 DP GPU 上、尚未写回 CPU 的前缀。共享 CPU 页可用于后续复用，但不保证与 GPU fetch 有相同命中率和时延。

7. 异常与资源回收

情况处理规则
CPU 未命中、不比 GPU 长或不值得恢复跳过复制，沿用 GPU 前缀；标记本次恢复完成，由主 rank 归还匹配页引用。
Router 排队期间取消尚未交给 Infer，由队列归还并清空匹配页引用。
CPU→GPU 搬运期间取消保持请求和页面存活，等搬运完成再归还 CPU 引用；不创建 PD 任务，随后释放 GPU 资源。
显存不足复制未提交时可放弃 CPU 恢复；尾部仍放不下，则在整组 PD 任务发布前终止。首 token 前通过已有 ServerBusy 通道唤醒仍在等握手的 Master，避免只发送结束 token 后一直等待；已产生输出的容量不足继续沿用原分段续跑。
CPU 复制 / CUDA 出错沿用进程失败与服务清理，不吞掉异常当作未命中，也不复用部分写入的数据。请求级恢复需单独设计回滚。
PD 取消、超时或失败保留有限次数的 abort 通知，等全部任务落定；有效长度回退到可信 GPU 共享前缀，持有容量按原值统一回收，失败尾部不进入缓存。
生成已结束，写回仍在进行不再计算或重复写回；完成后由主 rank 发布可复用页、归还引用，再释放 GPU 页和请求槽。
CPU 页不足只写回已分配的连续前缀，遇到分配失败就截断；一页也没有则跳过写回并退出。已有可复用页继续去重。

匹配引用在 Router→Infer 时转交，不能两边重复归还。Infer 统一管理已消费引用；不能因为共享列表非空就再次释放。若清空列表，须先让同副本所有 TP rank 读取同一快照，再由主 rank 清空。

保留现有计算流依赖、CUDA 事件和接收端复制完成检查，不增加全局设备同步。P 发送完成不能替代 D 本地完成。

性能评估

通常节省 L-G 个网络 KV token，但要单算零长度分支、页开销和 hybrid 运行态；整页 CPU 复制也可能覆盖部分 GPU 共享前缀。

          < 可省下的 PD 传输 / 页处理时间 + 确实能够省下的 P 计算时间
记录：实际新增复用 token、H2D / D2H 字节与耗时、P→D 字节与任务数、
      PD 等待、TTFT、TPOT、吞吐、引用和显存余量。

普通 PD 中，完整注意力若在 D 恢复到 N−1，握手后可以直接跳过 P，此时确实省下 P 计算；其余路径 P 的计算量取决于 P 自己的缓存，不能把 D 的传输缺口当成 P 的计算范围。Hybrid 的 D CPU 页只有 KV，必须保留运行态恢复；Prefill-first 的 P 已先完成计算，也不会自动省掉 P 的计算。

变慢原因：已确认路径与待测分项

  1. CPU 恢复位于普通 PD 的串行关键路径。D 在 load_cpu_cache_to_reqs() 完成后才通过回调提交接收任务；pd_normal_master.py 等待 upkv 后才把 Decode 信息发给 P，P 的 HTTP 请求在此之前尚未进入本地推理。因此对仍需 P 的路径，CPU 匹配、加载和完成轮询先于 P 计算，而不是与它重叠。
  2. 冷热请求都会增加控制面开销。D 的 HTTP 请求先进入多级缓存进程及其线程池，再发 Router；MultiLevelKVCacheManager.task_loop() 空闲时 sleep 5ms，接收和完成转发均可能遇到轮询相位等待；共享页匹配、加/减引用也有锁和对象开销。不能把 5ms 当作整条额外路径的准确耗时或上限。
  3. token 阈值没有自动估算实际收益。上述实测使用新增 KV≥128、输入≥256 且容量足够的门槛。Decode 现可通过 LIGHTLLM_DECODE_CPU_CACHE_MIN_LOAD_TOKENS 手动调整新增 KV 阈值，默认改为 2048，其他角色固定 128；这尚未比较本机 CPU→GPU 与 P→D 的有效速度、页任务开销，也没有区分能否省掉 P。Hybrid 热组 P 已有 4096-token 前缀，只需补末尾少量 token 与运行态，CPU 命中未节省这些工作；4096 token 的本模型 full-att KV 约为 48MiB，还需先从主存恢复。本机 GPU 两两拓扑为 NV18，原本的同机 GPU→GPU 传输成本可能较低，不能直接沿用跨机网络的收益预期。
  4. 主要观测是首 token 固定开销，并非已证明 decode 算力大幅降低。Hybrid Graph 关闭热组开/关的 TPOT 为 20.005 / 20.025ms；Graph 开启组为 5.983 / 5.704ms。短输出的请求级 TPS 容易被更长 TTFT 拉低。D2H、逐请求索引上传、事件和页元数据也可能影响下一请求和资源释放，但尚未分项剖析其贡献。

这些测试使用 Triton 异步 CPU IO，日志确认等待 recorded event，不是 FA3 的强制计算流同步路径。CPU-only 匹配只返回 ready 页，因此代码中为磁盘等页面保留的 10ms ready 轮询不能直接算作此次热请求慢因。GPU0–3 与 GPU4–7 分别靠近 NUMA0/1，CPU 页实际归属和绑核尚未测量；交换 GPU 不能消除主存位置这个变量。当前没有阶段级 CUDA event/控制面耗时数据，不能把测得的额外 22–42ms 全部归因于 H2D 或某个 sleep。

优化方案（待实现与验证）

顺序方案与入口验收与边界
1：补可观测性在 HTTP→匹配→Router、匹配队列/锁、实际 H2D 提交与 CUDA 完成、完成事件被调度观察、握手、P 计算及传输、首 token 处记录分段时间；区分实际复制字节与逻辑命中。异步采样记录 CUDA event，不在热路径全局 synchronize。同机/跨机、冷/热/部分/全命中、Graph、不同并发分别报告 p50/p95；先定位固定控制面与字节相关开销，避免凭总 TTFT 调 kernel。
2：减少匹配转发等待将多级缓存进程的 5ms 空轮询改为带工作线程完成通知的事件驱动 poll，合批发送完成队列；空 hash / 不可缓存请求增加不匹配快路径。GPU 已覆盖或 miss 时直接归还引用并回调，将 load stream 的创建和 wait 延后至确实需要拷贝。socket 仍由所属线程操作，不简单在 worker 跨线程发送。冷请求不需要 H2D，也应降低额外延迟；已匹配页的引用必须归还，保留取消、超时和队列背压。CPU-only 已只返回 ready 页，不需误删磁盘等待。
3：按收益决定加载在 load_cpu_cache_to_reqs() 分支用实际新增字节、PD 页任务数、历史有效 H2D/PD 耗时估算净收益，取代仅靠手动 token 阈值；普通 PD 的完整注意力 N−1 可加入“免 P”收益，Hybrid 与 Prefill-first 不加入。净收益不足时不加载，立即归还 CPU 引用并续接原 PD 路径。优先消除同机部分命中负收益，保留 GPU 淘汰后的完整命中收益。D 当前没有 P 的精确命中/排队信息，不能假装已知 P 计算节省量；先用保守估计和历史分组数据，再考虑元数据扩展。
4：减少搬运与写回固定开销评估共享 page-index Tensor、请求合批与连续区域拷贝；避免所有页已 ready 时仍准备多余索引/事件。记录 CPU 页 NUMA 归属，评估与 D GPU 对齐的绑核和内存首次触页。结合放置策略评估低复用 cold 写回，避免无收益的 D2H 和回收等待。跨 State/TP 的布局和副本完成协议保持一致；不能因部分页已 ready 而错位，也不能提前释放 GPU token。GPU 前缀与 CPU 页重叠只能在增加正确偏移/掩码后省略，不能直接裁短索引列表。
5：P 与 D 准备重叠对必须执行 P 的负载先评估已有 Prefill-first 模式；若普通 PD 仍需重叠，再设计提前 P 计算、延后传输的协议与资源预算。这属于协议级方案，不能在 CPU KV 未就绪时提前报告 ready_kv_len 或握手；需重做取消、容量与运行态恢复验收。Prefill-first 的首 token 来自 P，性能口径需单独比较。

后续仅增加 Decode 专用的加载阈值环境变量，采样计数仍保留 TODO，上述自动收益估算与其他性能方案尚未实现。已有功能开关仍按工作负载选择；在阶段数据和收益门槛落地前，不承诺所有命中都能降低延迟。
