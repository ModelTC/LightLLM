# PD 首块就绪后分配 KV

D 在收到 P 的首个 WRITE 请求后，才申请完整输入所需的 GPU KV 空间。此前 D 在初始化请求时就申请这部分空间，即使 P 尚未产出 KV，也会占住 D 的容量。

这里的“首块分配”指延迟一次完整输入分配，不是每传一块就扩容一块。后续 KV 仍按原有页面传输，可以与 P 的后续 prefill 重叠。没有动态水位、CPU 暂存或新的启动参数。

## 流程

1. D 发布连接和任务元数据，不申请目的 KV。
2. P 产出首块后发送 WRITE 控制消息，等待 D 的接收许可；等待期间不占用 P 的传输页。
3. D 检查实际可分配容量及已准入请求的输出增长余量，TP ranks 使用最小容量达成一致。空间不足则等待，取消和超时沿用失败清理流程。
4. 空间足够时，D 分配完整输入 KV，更新任务索引，再发 WRITE READY。P 随后申请源传输页并执行传输。

`running_max_req_size` 继续限制待分配及活跃请求总数。等待中的请求不预留完整输入 KV，但每个请求仍必须能单独放入 D。完整前缀命中保留已有免传输路径；部分前缀命中的引用在等待前释放，避免多个等待请求互相锁住容量，因此这类请求会重新传输完整输入 KV。P/D 应一起升级，混合版本未验证。

## 已有策略实验

以下是此前冻结实验实现中 `gpu_chunk` 与 `gpu_early` 的对照，用于说明选择首块策略的依据，**不是这份精简 PR 的 GPU 实测收益**。

- GLM-4.7-Flash；同机两张 H200，P/D 各一张；TP=DP=1；NIXL 0.8.0。
- P 容量 131,072 token，D 容量 24,576 token；8 个活跃 D 槽位，另有 8 个待准入槽位；关闭 CPU 暂存。
- 每类负载 24 个请求；seed=20261018；固定输出长度、忽略 EOS；提前分配先运行、首块策略后运行。
- 每类负载只有一个配对观测，未完成反向顺序和多 seed 重复，不能据此声称统计显著或可持续服务容量提高。

| 负载 | 输出吞吐变化 | 整体 TTFT P95 变化 |
| --- | ---: | ---: |
| 等长请求 | +5.83% | −5.64% |
| 长短混合 | +25.05% | −21.53% |
| 队头阻塞 | +21.85% | −18.98% |
| 泊松到达 | +22.91% | −27.26% |
| Decode 密集 | +0.43% | −1.23% |

各策略 120/120 个测量请求成功，逐请求生成 token 序列一致。总体改善不代表所有请求类别都受益：队头阻塞负载中，16 个短输入请求的 TTFT P95 从 **5.328 秒上升至 6.113 秒（+14.72%）**。

原实验支持“容量紧张时避免过早占位”的方向。本 PR 保持原有总请求上限，没有纳入研究实现的额外待准入槽位，因此不能承诺复现上表百分比。精简提交尚未做 GPU 端到端重测。脱敏数值、输入长度分布/到达跨度、版本和原始结果摘要哈希见 [pd_first_chunk_results.json](pd_first_chunk_results.json)。该 JSON 用于核对本表，不包含运行完整实验所需的冻结源码和全部原始日志。

## 验证

75 项 CPU 回归通过，覆盖首个 WRITE 前零分配、容量与输出增长预留、TP 容量取最小值、DP 后端委托、分页对齐、混合注意力任务、前缀处理、重复通知、取消及超时竞争、共享请求复用，以及 P 传输页耗尽时仍可发送就绪通知。GPU 实验保持停止，没有重新占用实验卡。
