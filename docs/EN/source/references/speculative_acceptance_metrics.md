# Speculative acceptance statistics

`--enable_spec_acceptance_metrics` enables per-request acceptance statistics in
`normal` serving mode. It is disabled by default. Prefill/decode disaggregation
(PD) does not support this option because final metadata is not transferred
between the prefill and decode roles.

For `/generate`, set `return_details=true` to include `spec_acceptance_metrics`
in the final token details. For `/generate_stream`, the final server-sent event
includes this field and the final native speculative-decoding counters.

Statistics are grouped by verification width and accepted draft-prefix length.
Each verification round also produces one target token. Initialization rounds
after initial or resumed prefill are stored under `bootstrap`, separately from
rounds generated by the draft model under `proposals`. Reusing a request slot
starts a new history.

When `proposals.rounds` is nonzero, the mean acceptance length is
`1 + proposals.accepted_draft_tokens / proposals.rounds`, including one target
token per proposal round. Per-position statistics contain two denominators:

- `accepted / proposed`: the fraction of proposals that accepted the prefix
  through this position, among proposals containing this position.
- `accepted / reached`: the conditional acceptance rate at this position after
  all preceding draft tokens were accepted.

Verification statistics are recorded before end-of-sequence (EOS) and output
length truncation. They include verified output that may be discarded when a
request finishes. `visible_output_tokens` and `inferred_output_tokens` report
visible and inferred output lengths; `verification_output_ranges` records the
corresponding ranges. The `committed` fields report output retained within the
visible output length. Its mean output length per contributing proposal round
is `committed.output_tokens / committed.proposal_rounds` when that denominator
is nonzero. Rounds with no visible output are counted in
`committed.unused_proposal_rounds`.

Final counters and histograms use the same snapshot at request release. If
HTTP metadata was assembled before an overlapping verification completed,
`http_counter_snapshot` preserves the earlier counters for comparison. The
final response uses the counters from the release-time snapshot.
